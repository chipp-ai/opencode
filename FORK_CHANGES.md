# Fork changes

This is [chipp-ai/opencode](https://github.com/chipp-ai/opencode), a public fork of [anomalyco/opencode](https://github.com/anomalyco/opencode). This file tracks everything this fork has added or changed on top of upstream, so anyone landing here knows what's different without diffing branches by hand.

Each entry names the upstream gap it addresses, whether it originated as our own work or was adapted from an abandoned community attempt upstream, and where to look for the actual commits.

## Implemented

### Auto-discover models from OpenAI-compatible providers

A configured provider can opt in (`discover: true`, or the v1 config's `discoverModels: true`) to have opencode call `GET {baseURL}/models` and add whatever the endpoint reports to the catalog, instead of requiring every model to be hand-listed — useful for LM Studio, vLLM, llama.cpp/llama-swap, or any generic OpenAI-compatible self-hosted endpoint.

- **Upstream gap:** [anomalyco/opencode#6231](https://github.com/anomalyco/opencode/issues/6231) — **247 reactions/57 comments**, the second-highest reaction count found across a full survey of this repo's open issues. Three substantial PRs sat open and unmerged for 3+ months despite that reaction count (protected from the usual bot auto-close, just never actioned by a maintainer): [PR #32731](https://github.com/anomalyco/opencode/pull/32731) (8 files, tightly scoped — primary source), [PR #42660](https://github.com/anomalyco/opencode/pull/42660) (75 files, broader scope — only its URL-with-existing-path handling was reused), and [PR #27554](https://github.com/anomalyco/opencode/pull/27554) (100+ files, over GitHub's diff-preview limit — nothing usable found beyond confirming its scope overlaps #32731's).
- **Origin:** implemented by an Opus 5 agent. Reused from #32731: the `discoverModels` config field name, which limit fields to read from the response (`context_length`, `max_context_length`, vLLM's `max_model_len`, `max_output_tokens`), the discovered-model shape, the "configured/models.dev wins" merge rule, and its failure-mode test cases. Deliberately changed from #32731: discovery is **opt-in per provider** here, not automatic for every provider with a `baseURL` — always-on would fire a startup network request at every existing custom provider, a behavior change too large to make silently. Unknown limits are left at `0` ("unknown" elsewhere in this codebase already) rather than #32731's guessed 128k default. #42660's standalone fetch helper was rewritten using this repo's own `HttpClient`/`Schema` idioms instead of raw `fetch` in a `try`/`catch`; its UI button, `POST /provider/discover` endpoint, and translations weren't ported. New, since none of the three PRs target it: a v2 `Catalog.Service` plugin (this repo didn't have a plugin/catalog system when those PRs were written).
- **Where:** runs in both of this repo's provider surfaces — the legacy provider service (`packages/opencode/src/provider/provider.ts`, inline before the filter pass, what the TUI model picker reads today) and a new v2 Catalog plugin (`packages/core/src/config/plugin/provider-discovery.ts`, registered in `packages/core/src/plugin/internal.ts`, running once at startup then every 60 minutes on the same schedule as the models.dev refresh). Shared discovery logic lives in new `packages/core/src/provider-discovery.ts`.
- **Known gaps:** the legacy provider service has no periodic refresh — a newly-loaded local model only appears after a restart/reload (the v2 side refreshes hourly). A model listed in config or models.dev but no longer returned by the server stays visible (nothing hides stale entries). Discovered capabilities are guesses (text in/out, tools enabled) — vision/reasoning support isn't reported by `/models` and isn't detected. Only the standard OpenAI `{data: [{id}]}` response shape is understood — Ollama's own native `/api/tags` isn't (its OpenAI-compatible `/v1/models` endpoint works fine). No settings UI, "discover now" button, or HTTP endpoint. The legacy side only checks a stored credential or `options.apiKey`, not plugin-based OAuth loaders.
- **Verified:** `bun typecheck` clean across all 30 packages. New tests: `packages/core/test/provider-discovery.test.ts` and `test/config/provider-discovery.test.ts` (unit-level, the merge rules and failure handling), `packages/opencode/test/provider/discovery.test.ts` (runs against a real local `Bun.serve` server, not a mock). Full suites (re-verified against this fork's current `dev`, not just the agent's own stale worktree base): `packages/core` 1187 pass (only the pre-existing `pty` flake); `packages/opencode` 3617 pass, only the 4 pre-existing, confirmed-unrelated `cf-ai-gateway` failures. `bun run generate` from `packages/client` correctly produced no changes — `discoverModels` is a config-only field, not a Protocol/HttpApi schema change. **Live-verified** against a real running server with `discoverModels: true` pointed at a local fake OpenAI-compatible `/models` endpoint: `discovered-model-1` (with its reported `context_length: 8192`) appeared in the live V2 model catalog alongside the three hand-configured models, whose own limits were correctly left untouched.
- **Where:** [`dev` branch history](https://github.com/chipp-ai/opencode/commits/dev).

### Unqueue / edit queued messages (V2 backend)

A durable, V2-native way to remove or edit a message that's been admitted but not yet promoted into a visible turn — new `SessionV2.pending`/`withdraw`/`revise` methods, three new HTTP routes, and a TUI `/queue` dialog. **Not yet reachable from the real TUI** — see known gaps.

- **Upstream gap:** [anomalyco/opencode#4821](https://github.com/anomalyco/opencode/issues/4821) — 126 reactions. [PR #6415](https://github.com/anomalyco/opencode/pull/6415) "Easy Message Unqueue with /unqueue" (9 files) was closed by a 60-day-stale bot, never reviewed. [PR #6271](https://github.com/anomalyco/opencode/pull/6271) "add edit and discard actions for queued messages" (11 files, more thorough — both edit and discard) was self-closed by the author after apparent lack of maintainer response, not a merit rejection.
- **Origin:** implemented by an Opus 5 agent, with an unusually important caveat flagged up front in its own research: both upstream PRs remove a queued message from an *in-memory callback list* and delete the V1 message — a backend model with no equivalent in this repo's V2 session core, where a queued message is a *durable row* that stays pending until a safe promotion point (see this repo's own `AGENTS.md`: "An explicit `queue` input remains pending until the Session would otherwise become idle; promote one queued input at that boundary..."). So the backend here is a fresh, V2-native design — not a port — built the same way `SessionInput.Prompted`/`projectPrompted` already work: a durable event (`session.next.prompt.withdrawn` / `.revised`) is published and then projected into a `withdrawn_seq` column (new, migration `20260923161657_session_input_withdrawn`) or a replaced `prompt` value, with the update guarded to only affect rows that are neither promoted nor withdrawn (racing a withdraw against an in-flight promotion resolves in the withdraw's favor — the runner skips answering a turn that no longer has anything pending for it). What *was* reused from the PRs: the "remove" and "edit" concepts themselves, `/unqueue` kept as a command alias (from #6415), and the general shape of a queued-message picker UI (from #6271) — reworked as a `/queue` list dialog (select a message to edit its text, or press ctrl+d twice to remove it) rather than #6271's inline "EDITING" mode in the main prompt box.
- **Where:** `packages/core/src/session/input.ts` (`listPending`/`withdraw`/`revise`/the new `NotPending` error), `packages/core/src/session.ts` (`SessionV2.pending`/`withdraw`/`revise`), `packages/core/src/session/runner/llm.ts` (a `requireInput` flag threading through the turn loop so a turn whose only justification was a withdrawn input is skipped rather than run with nothing to answer — merged by hand against this fork's own model-fallback feature, which had already added a different parameter to the exact same functions), three new routes (`GET /api/session/:id/input`, `PATCH .../input/:messageID`, `DELETE .../input/:messageID`) in `packages/protocol/src/groups/session.ts` + `packages/server/src/handlers/session.ts`, and a new `packages/tui/src/component/dialog-queued-input.tsx` + `/queue` command.
- **Known, significant gap — read before relying on this:** the TUI still sends every prompt through the legacy V1 `SessionPrompt` path, which never creates the V2 `session_input` rows this feature acts on. **`/queue` will show an empty list for anything typed in the actual running TUI today.** Switching the TUI to send V2 prompts (`delivery: "queue"`) would make this feature real end-to-end, but is a materially bigger decision (it changes how every prompt in the TUI is sent) than this feature's own scope, and was deliberately left for a separate follow-up rather than silently expanded into. The backend is fully real, tested, and reachable via the HTTP API directly today. Also: the web app's own queue UI keeps its queue in the browser and doesn't call these routes; there's no "QUEUED"/"EDITING" badge on messages in the transcript; editing changes text only, not attachments or agent mentions; withdrawal also applies to a not-yet-promoted default-"steer" message, not just explicitly-queued ones (the dialog labels those "next turn"); the TUI dialog itself has no render test (only its data layer and API calls are tested).
- **Verified:** `bun typecheck` clean across all 30 packages. New tests: `packages/core/test/session-prompt.test.ts` (+10 cases — a withdrawn message never reaches the model and the next queued one still runs; withdrawing the only queued message adds no extra model call; withdrawing an already-promoted message is rejected; an edited message runs with the edited text; a promotion that loses the race to a withdraw is refused; double-withdraw/unknown-id/wrong-session/retry-after-withdraw are all rejected), `packages/core/test/session-runner.test.ts` (+4), `packages/tui/test/cli/tui/data.test.tsx` (+2), three new `httpapi-exercise` scenarios, and an updated `event-manifest.test.ts` event count (88 → 90 for the two new durable events). Client and legacy JS SDKs regenerated. Full suites (re-verified against this fork's current `dev`, including the manual merge against model-fallback's own changes to the same runner functions): `packages/core` 1178 pass (only the pre-existing `pty` flake); `packages/opencode` 3613 pass, only the 4 pre-existing, confirmed-unrelated `cf-ai-gateway` failures; `packages/tui` 230 pass; `httpapi-exercise` coverage mode 214 pass (only the pre-existing, unrelated missing `/api/session/{sessionID}/cost` scenario). **Live-verified** against a real running server: queued a second and third input mid-turn (delaying the first turn with a scripted slow response to create a real race window), listed them via `GET .../input`, withdrew one and revised the other's text via the real HTTP routes, confirmed the pending list reflected both changes immediately, then let the turn finish and confirmed exactly one continuation turn ran afterward — using the revised text, not the withdrawn message.
- **Where:** [`dev` branch history](https://github.com/chipp-ai/opencode/commits/dev).

### Find-in-session (TUI)

Search within the current session's message history in the TUI — open with `<leader>f` or `/find` (alias `/search`), type a query, step between matches with Enter/Shift+Enter, Esc to close.

- **Upstream gap:** [anomalyco/opencode#4714](https://github.com/anomalyco/opencode/issues/4714) — 67 reactions/35 comments. Unusually, the relevant PRs were still open and unreviewed rather than bot-closed: [#45037](https://github.com/anomalyco/opencode/pull/45037) and [#48470](https://github.com/anomalyco/opencode/pull/48470) (a duplicate, #48088, was closed within 2 hours by a PR-template-compliance bot). Neither PR actually targets the TUI — both add Cmd/Ctrl+F search to the web/desktop timeline (`packages/app`/`packages/session-ui`), competing for the same web feature rather than being two different asks.
- **Origin:** implemented by an Opus 5 agent. #45037's approach (reusing the file viewer's search by scanning the rendered page) can't carry over to a terminal UI and wasn't used. #48470's approach — find matches directly from message *data* (text, reasoning, tool inputs, error rows), then scroll to the hit — doesn't depend on a browser, so this fork's matching logic (`partSearchText`, `findMatches` in the new `packages/tui/src/util/session-find.ts`) is ported from it directly. Its browser-only parts (DOM text highlighting, the web find-bar component, file-viewer shortcut sharing) have no TUI equivalent and were rewritten as a real terminal find-bar component (new `packages/tui/src/routes/session/find.tsx`) plus new match-navigation (`highlightSegments`, `stepIndex`) and scroll-target logic, since a terminal UI has no DOM to highlight or scroll natively.
- **Where:** four new overridable keybinds (`session_find` `<leader>f`, `session_find_next`, `session_find_previous`, `session_find_close`) in `packages/tui/src/config/keybind.ts`; the `/find`/`/search` command and rendering wiring in `packages/tui/src/routes/session/index.tsx` (matched parts get a highlighted background, stronger on the current match; a collapsed "Thought" block auto-opens while it holds the current match; the prompt hides while the bar is open).
- **Known gaps:** word-level highlighting only works in user messages — assistant replies/reasoning/tool rows highlight as a whole block, since the terminal rendering library can't highlight part of a rendered markdown block. Tool *output* isn't searched, only tool *inputs* (commands, paths, patterns) — matching #48470's own choice, since most tool output is collapsed by default. A match inside a hidden/collapsed region (a completed tool call's hidden details, or shell output beyond the first 10 lines) is counted but has nothing on screen to jump to. Only the current session is searched — no cross-session or child-session search. The keybinds docs page and generated SDK types don't list the new `session_find*` keys yet.
- **Verified:** `bun typecheck` clean in `packages/tui`. New `packages/tui/test/util/session-find.test.ts` (11 unit tests, adapted from #48470's own test file) plus a new `packages/tui/test/cli/tui/session-find.test.tsx` (2 tests rendering the real find bar, matching this repo's `dialog-prompt.test.tsx` pattern — typing, next/previous, the match counter, Esc closing the bar without leaking to the session's own Esc-interrupts-the-turn handler, and keybind overriding). Full `packages/tui` suite (re-verified against this fork's current `dev`, including the expandable-pasted-text-placeholders feature above which touches two of the same files with no conflict): 228 pass. **Live-verified** against the real TUI in a tmux session (a scripted fake OpenAI-compatible backend, two prompts each producing a matching "needle" reply): opened with `ctrl+x f`, typed `apples` and got the correct `1/1`, typed `needle` and got the correct `4/4` (both user prompts and both replies), Enter/Shift+Enter changed the match index, and Esc closed the bar cleanly back to the normal prompt. (One earlier attempt in the same long-lived tmux pane, after many prior command-palette interactions, saw typed characters not reach the input at all — reproduced as a stale focus/mode-stack state from that specific interaction history, not from a clean open; a fresh session made it disappear, so it's noted here rather than filed as a confirmed bug.)
- **Where:** [`dev` branch history](https://github.com/chipp-ai/opencode/commits/dev).

### Expandable pasted-text placeholders

A pasted `[Pasted ~N lines]` placeholder in the TUI prompt can now be expanded to its full content and collapsed back — click it, or run "Expand/collapse pasted text" (`prompt.paste.toggle`) from the command palette or a keybind.

- **Upstream gap:** [anomalyco/opencode#8501](https://github.com/anomalyco/opencode/issues/8501) — **325 reactions**, the single highest-reaction issue found across a full survey of this repo's open issues. A trivial 1-file fix already merged upstream as PR #39920, but the issue stayed open because that fix is a one-way, no-collapse click-to-expand, not the real ask — and it isn't even present on this fork's history (its merge commit exists but isn't an ancestor of `dev`). Richer attempts, all closed by the automated PR-cleanup bot (>1 month old, <2 reactions) and never reviewed: [PR #41813](https://github.com/anomalyco/opencode/pull/41813) "paste expand toggle" (primary source), [PR #33700](https://github.com/anomalyco/opencode/pull/33700) "expand pasted text placeholders literally", and the tokens/sec-bundled [PR #37052](https://github.com/anomalyco/opencode/pull/37052) (only its expand-related idea used; the rest is unrelated and was independently ported for the tokens/sec feature above).
- **Origin:** implemented by an Opus 5 agent. #41813's logic is reused almost as-is: a pasted-text part remembers its original placeholder so it can collapse again after expanding, the chip is swapped by deleting its extmark, replacing the selected text, and recreating the extmark over the new text, and a guard stops the prompt's own content-change sync from dropping the part mid-swap. #33700 fixed a real, separate bug reused as-is: `expandPastedTextPlaceholders` used to substitute pasted text back in via `String.replace(str, str2)`, which treats `$&`/`$$`/etc. in the pasted text as special replacement patterns and silently corrupts it — fixed by passing a replacer function instead of a literal string. #37052 contributed only the idea of a palette command to expand chips (its own version was one-way, collapse-all); this fork's version is a proper toggle on the chip under the cursor. Two pure, newly-extracted, unit-tested functions (`togglePastedText`, `replaceVirtualExtmarkText` in `packages/tui/src/prompt/part.ts`) hold #41813's logic so it's testable outside the full `Prompt` component. New: older saved prompts with no stored placeholder (from before this field existed) can still be expanded, where #41813's own version would lock them collapsed-only; `try`/`finally` around the swap was dropped per this repo's avoid-`try`/`catch` convention.
- **Where:** `packages/tui/src/component/prompt/index.tsx` (click handling + the new `prompt.paste.toggle` command), `packages/tui/src/prompt/part.ts` (the two extracted pure functions), `packages/tui/src/prompt/history.tsx` (a `placeholder` field on the saved pasted-text-part type), `packages/tui/src/config/keybind.ts` (a `prompt_paste_toggle` keybind slot, unbound by default like other prompt commands).
- **Known gaps:** the full `Prompt` component's actual mouse-click path (as opposed to the pure toggle/swap functions) has no test — mounting it needs SDK/sync/route providers with no existing fixture for that; the click behavior was checked manually against a bare `<textarea>` firing the same mouse events instead. Clicking a chip's very last character can miss (the cursor then sits just past the chip's end, which the editor library's extmark lookup doesn't count as "inside" it) — the same limitation exists in #41813. An expanded chip remains a single cursor unit with the paste-highlight style; its text is viewable but not editable in place, matching #41813.
- **Verified:** `bun typecheck` clean in `packages/tui`. New tests in `packages/tui/test/prompt/part.test.ts` (pure toggle/collapse cases) and a new `packages/tui/test/prompt/paste-toggle.test.tsx` (using a real `<textarea>` via this repo's existing `testRender`/`mockMouse` test helpers, matching `test/cli/tui/dialog-prompt.test.tsx`'s established pattern) covering expand/collapse in place, later chips shifting correctly after a swap, and the cursor landing inside the chip after a click. Full `packages/tui` suite (re-verified against this fork's current `dev`, not just the agent's own stale worktree base, and after the tokens/sec feature above): 215 pass. **Live-verified** against the real TUI in a tmux session: a real bracketed multi-line paste (7 lines) produced the `[Pasted ~7 lines]` chip; running "Expand/collapse pasted text" from the command palette expanded it to all 7 full lines in place, and running it again collapsed it back to the chip.
- **Where:** [`dev` branch history](https://github.com/chipp-ai/opencode/commits/dev).

### Per-call subagent model selection (Task tool)

The primary agent can now override which model a specific `task` dispatch uses (`model: "provider/model-id"`, plus an optional `variant`), instead of every dispatch always using the subagent's statically-configured model.

- **Upstream gap:** [anomalyco/opencode#6651](https://github.com/anomalyco/opencode/issues/6651) — 86 reactions/44 comments, an unusually high comment:reaction ratio for a contested, actively-discussed ask. At least 6 independent implementations over ~8 months, all unmerged. [PR #34947](https://github.com/anomalyco/opencode/pull/34947) (open since July, 13 files) is the consolidated, community-endorsed design, explicitly superseding two earlier attempts and closing 5 related issues — still sitting open and unreviewed 2.5+ months later. [PR #35800](https://github.com/anomalyco/opencode/pull/35800) (open, 4 files, smaller focused variant) is the primary source actually used.
- **Origin:** implemented by an Opus 5 agent. The core mechanism (single `ctx.ask` permission gate, override-first model resolution, reusing the existing `Provider.parseModel`) comes from #35800. The `variant` parameter and its "always allow" permission behavior come from #34947. #34947 defaulted the new permission to `"deny"`; this fork defaults to `"ask"` instead, so the feature works out of the box without extra config.
- **Where:** `packages/opencode/src/tool/task.ts` (`model`/`variant` parameters on the `task` tool, a new `model_override` permission — `"ask"` by default, pre-allowable per model pattern e.g. `{"model_override": {"anthropic/*": "allow"}}`), `packages/opencode/src/agent/agent.ts` (the permission default).
- **Known gaps:** the override model isn't validated up front — a nonexistent model passes the permission prompt and only fails when the subagent actually runs, surfacing as a normal (resumable) task failure. No typed config key for `model_override` yet (works as a free-form permission key, but has no generated SDK type or docs entry — adding one means regenerating the client). A resumed task (`task_id` + no `model`) doesn't remember a prior override; it re-resolves fresh each call. No TUI for picking a model per dispatch (the permission prompt shows the requested model in its metadata, nothing more). Only the legacy V1 Task-tool dispatch path is covered — V2 `SessionRunner`/`AgentV2` task dispatch doesn't get this. Deliberately left out of #34947's fuller scope: slug task IDs, `resume`, `timeout`, `fallback_model` (would overlap with this fork's own model-fallback feature), `metadata`, `cancelRun`.
- **Verified:** `bun typecheck` clean in `packages/opencode`. New tests in `packages/opencode/test/tool/task.test.ts` (10 cases: configured model, parent fallback, override winning over configured model, multi-slash provider ids like `openrouter/anthropic/claude-sonnet-4`, variant inheritance rules, malformed input rejected before dispatch, the permission ask firing only when an override is requested, denial stopping the dispatch) plus a new default-permission test in `test/agent/agent.test.ts` and updated snapshots in `test/tool/parameters.test.ts`. Full `packages/opencode` suite (re-verified against this fork's current `dev`, not just the agent's own stale worktree base): 3613 pass, only the 4 pre-existing, confirmed-unrelated `cf-ai-gateway` failures. **Live-verified** against a real running server (V1 `POST /session/:id/message`, a scripted fake LLM backend): a `task` call with `model: "fake/backup"` against a subagent configured with a different default model (`fake/spare`) produced a real child session whose recorded metadata shows `model: {providerID: "fake", modelID: "backup"}`; a control call with no `model` field produced a child session correctly using the configured default (`spare`) instead.
- **Where:** [`dev` branch history](https://github.com/chipp-ai/opencode/commits/dev).

### Monitor tool (background watch)

A gated `monitor` tool (plus `monitor_list`/`monitor_stop`) lets the model watch a long-running background command's output for a pattern, or until it exits, and get notified back into the session — a standing watch, not just a one-shot check. Analogous to Claude Code's own Monitor tool.

- **Upstream gap:** part of the same feature space as [anomalyco/opencode#49842](https://github.com/anomalyco/opencode/issues/49842) (open) and related asks. [PR #33806](https://github.com/anomalyco/opencode/pull/33806) "feat: add Monitor tool" (1,398 lines, 11 files) is the primary source — closed by the automated PR-cleanup bot, never reviewed. Also considered [#44191](https://github.com/anomalyco/opencode/pull/44191) (a cron scheduler, closed by the same bot the same week this was researched, praised by a human reviewer before the bot closed it anyway) and the [#47166](https://github.com/anomalyco/opencode/pull/47166)/[#47193](https://github.com/anomalyco/opencode/pull/47193)/[#47284](https://github.com/anomalyco/opencode/pull/47284) durable-heartbeat resubmits (each closed within hours by a 2-hour PR-template-compliance bot, never reviewed) — neither ported, see known gaps.
- **Origin:** implemented by an Opus 5 agent, built directly on this repo's existing `BackgroundJob` primitive rather than modifying it. Reused nearly word-for-word from #33806: the tool's parameter shape ("same description re-arms/replaces, different description runs a second concurrent monitor"), the session-scoped list/stop logic, the untrusted-output fence with an unpredictable id (so watched output can't forge its own closing tag), control-character stripping, the permission-grant rule (never grant "always" for a command containing a glob character, since the stored pattern would then match as a glob), the detached-process-plus-parent-death-watchdog design, the flood guard, and most of the tool description and test scenarios. Rewritten rather than ported: #33806 modified core `BackgroundJob` itself to add a `WakeScope` avoiding a self-re-arm deadlock — this fork's version avoids the core change entirely by forking notifications into the tool's own scope, the same pattern `task.ts` already uses; #33806's hand-written reader/debounce became an Effect `Stream` pipeline; its base64 command-wrapper (a workaround for a `Shell.args`/`eval` issue in its target repo) isn't needed here since this repo's bash tool already runs commands through plain `ChildProcess.make`; permission goes through the existing `bash` permission rather than a new separate one, so existing bash rules govern monitors too.
- **A real, generalizable bug found and fixed along the way:** a command that writes output continuously with no pause (e.g. `yes`) hung teardown and starved timers, because the way this repo's Effect version reads a child process's stdout never yields control back to the scheduler while data keeps arriving. Fixed with a single `Stream.tap(() => Effect.yieldNow)` in the read pipeline (documented inline) — the same issue could affect any other `handle.stdout` reader facing a non-pausing producer, worth checking separately.
- **Where:** gated behind `OPENCODE_EXPERIMENTAL_MONITOR` (or `OPENCODE_EXPERIMENTAL=1`), matching the existing `experimentalBackgroundSubagents` convention. New `packages/opencode/src/tool/monitor.ts` (~360 lines: `monitor`/`monitor_list`/`monitor_stop`) + `monitor.txt` (tool description).
- **Known gaps (deliberately scoped, not silently dropped):** not durable — monitors live in memory only; a restart or project close stops them with no record (the tool description tells the model this explicitly). No scheduler — "check every N minutes" only works as a shell poll-loop inside the watched command; #44191's cron subsystem wasn't ported (the human reviewer's own concerns about it — a job firing once after deletion, deliveries reaching a closed project, a "5m" schedule firing immediately — would need fixing first, and it's a genuinely separate subsystem). `opencode run`'s non-interactive mode exits once the session goes idle, which kills active monitors. No UI — monitors are only visible to the model via `monitor_list`, nothing in the TUI/web/HTTP surface. Notifications call `prompt(...)` directly rather than queueing, so one landing while the session is busy joins the running turn instead of queueing on its own. Only stdout is read (not stderr); lines are capped at 4000 characters; a 5000-line flood auto-stops a monitor. The parent-death watchdog is POSIX-only — skipped on Windows. No external delivery (webhooks) — #46687 wasn't pulled in. **Found during live testing:** like the Task tool's own per-call model selection above, this tool only exists in the legacy V1 tool tree (`packages/opencode/src/tool/monitor.ts`, registered in `packages/opencode/src/tool/registry.ts`). `packages/core/src/tool/builtins.ts` — the tool set V2 `SessionRunner` actually resolves against — has a standing, pre-existing TODO ("Port the remaining launch-follow-up leaves deliberately: edit fuzzy parity, task, LSP, ...") that already excluded `task`/`lsp` before this session; `monitor` was added into the same not-yet-ported tree and inherits the same limitation. A model running under a V2 session gets `Unknown tool: monitor` if it tries to call it — confirmed live (see Verified).
- **Verified:** `bun typecheck` clean in `packages/opencode`. New `packages/opencode/test/tool/monitor.test.ts` (13 tests: self-cancel re-arm without deadlock, concurrency, list/stop by id and description, byte-flood guard, multi-line commands) passes 3 runs in a row. Full `packages/opencode` suite (re-verified against this fork's current `dev`, not just the agent's own stale worktree base): 3600 pass, only the 4 pre-existing, confirmed-unrelated `cf-ai-gateway` network-dependent failures. **Live-verified** against a real running server (V1 `POST /session/:id/message`, a custom OpenAI-compatible provider backed by a local scripted fake LLM): the model called `monitor` against a real shell command, which spawned a real child process; the watched stdout arrived back as two separate synthetic messages (correctly batched — two `echo`s a second apart stayed un-coalesced) inside the documented anti-forgery `<monitor_output id="...">` fence, followed by the correct exit notification once the command finished. ### Live tokens/sec display

The TUI now shows generation speed while an assistant response streams (`▣ Build · <model> · ~NN tok/s`, refreshing every 500ms) and a final rate once the turn completes.

- **Upstream gap:** [anomalyco/opencode#5374](https://github.com/anomalyco/opencode/issues/5374) — 111 reactions. Two small PRs existed, both closed by automated bots and never reviewed: [#46882](https://github.com/anomalyco/opencode/pull/46882) (closed by the 2-hour PR-template-compliance bot, same day) and [#42372](https://github.com/anomalyco/opencode/pull/42372) (closed by the 1-month/low-reaction bot; targets the web app, only computes a rate after the turn ends).
- **Origin:** implemented by an Opus 5 agent. The footer placement and refresh approach come from #46882, which already targeted `packages/tui`. The ~4-characters-per-token live estimate and the "only count text/reasoning parts" rule are also from #46882. The "show a rate after completion too" idea is from [#37052](https://github.com/anomalyco/opencode/pull/37052) (a bundled PR also containing an unrelated paste-expand feature — only the tokens/sec piece was used) — but #37052's own final-rate formula was rewritten because it counted input and cache tokens, badly inflating the number; this fork's version counts only output and reasoning tokens. New: the measurement window starts at the first streamed token rather than message creation (so waiting for the first token doesn't deflate the rate) and stops at the last finished text/reasoning part (so time spent running tools doesn't either).
- **Where:** new `packages/tui/src/util/throughput.ts` (~40 lines: `tokensPerSecond`, `liveTokensPerSecond`, `finalTokensPerSecond`), wired into the assistant-message footer in `packages/tui/src/routes/session/index.tsx`.
- **Known gaps:** the live number is a character-count estimate (`~4 chars/token`), not exact — providers only report real output-token counts at step-finish, and getting an exact live rate would require Core to send usage mid-stream, which wasn't touched here. Each tool step gets its own assistant message with its own footer, so the shown rate is for the final step of a turn, not averaged across the whole turn. An interrupted response shows no rate (it never gets a completed timestamp).
- **Verified:** `bun typecheck` clean in `packages/tui`. New `packages/tui/test/util/throughput.test.ts` (9 tests) covers the rate math, the under-1-second cutoff, a growing stream sampled over time, text+reasoning summed together, tool time excluded, missing-timestamp fallback, and the final-rate formula ignoring input/cache tokens. Full `packages/tui` suite: 208 pass (re-verified against this fork's current `dev`, not just the agent's own stale worktree base). **Live-verified** against the real TUI in a tmux session, driven by a scripted fake backend that streamed a 40-word reply one word at a time (120–150ms apart) and reported real usage on the final chunk: mid-stream, the footer showed a live character-estimate rate (`~13 tok/s`) while only half the words had arrived; after completion it showed a real-token-count final rate (`6.2s · 7 tok/s`) computed from the reported `completion_tokens` and the actual generation window — confirming both the live estimate and the final real-count formula work end-to-end, not just in unit tests.

### Model fallback on exhausted retries

When a provider/model keeps failing after `RequestExecutor`'s transport retry budget is spent (429/5xx/529), the V2 session runner now fails over to the next model in the agent's configured `fallback` chain instead of erroring the turn out to the user.

- **Upstream gap:** [anomalyco/opencode#7602](https://github.com/anomalyco/opencode/issues/7602) (open tracking issue) and [#48991](https://github.com/anomalyco/opencode/issues/48991) (open). Reinvented independently at least five times — [PR #49125](https://github.com/anomalyco/opencode/pull/49125) (open, unmerged), [#26292](https://github.com/anomalyco/opencode/pull/26292) (open, unmerged), [#27939](https://github.com/anomalyco/opencode/pull/27939), [#42424](https://github.com/anomalyco/opencode/pull/42424), [#35188](https://github.com/anomalyco/opencode/pull/35188) (all closed unmerged by the same automated PR-cleanup bot, none rejected on the merits) — plus a working third-party plugin (`@shutovks/opencode-model-fallback`) that already does this outside the repo.
- **Origin:** implemented by an Opus 5 agent, instructed to reuse the real upstream diffs rather than write from scratch. Fetched and read #49125, #26292, #27939, and #35188 directly via `gh pr diff`. #35188 turned out to already target this repo's V2 session runner (the other PRs patch the legacy V1 `processor.ts`, which per this repo's `AGENTS.md` new orchestration code must never bridge through) and became the primary source: the `fallback: []` config schema shape, and the general approach, are adapted from it. The retry-exhaustion classifier's names/shape come from #49125; its actual logic reuses `RequestExecutor`'s existing `LLMError.retryable` flag (in `packages/llm/src/route/executor.ts`) as the single source of truth for "is this retryable" rather than re-deriving a second status-code list. Model-switch attribution is recorded via the session's existing `SessionEvent.ModelSwitched` event rather than mutating an in-flight input object in place — a lesson taken directly from #27939's writeup of a real bug in its own V1-era approach (mutating a spread-copied object silently drops the write).
- **Where it lives:** `agents.<name>.fallback` (an array of model refs) in config, mirroring how `model` is already set per agent; also accepted on the older top-level `agent:` config format. New `packages/core/src/session/runner/fallback.ts` (the `shouldFallback` classifier + `candidates` resolver, ~40 lines) and matching changes to `packages/core/src/session/runner/llm.ts` (a new `ContinueAfterFallback` turn-transition, following the exact pattern already used for post-compaction turn continuation), `packages/schema/src/agent.ts`, `packages/core/src/config/agent.ts` (+ plugin/v1 config variants).
- **Known gaps (honestly scoped, matching this fork's usual discipline):** the fallback switch is sticky for the rest of the session (no cooldown/return-to-primary, unlike #26292's cooldown manager); no mid-stream failover once assistant output has started; only provider errors marked `retryable` trigger a switch, so some in-stream errors (e.g. Anthropic's `overloaded_error` inside a 200 response) won't, while an equivalent HTTP 529 status will; fallback is per-agent only, not per-model or global; a fallback model always uses its default variant, not the originating session's; no TUI toast or docs update yet.
- **Verified:** `bun typecheck` clean across all 30 packages. New `packages/core/test/session-runner-fallback.test.ts` (9 tests) exercises real `RequestExecutor` retry counts against a scripted fake HTTP client — asserting exact call sequences (e.g. primary × 3 retries → backup), correct session projection (a `model-switched` message inserted, no leaked failed assistant message from the aborted primary attempt, correct final session model), chain-walking with an unresolvable model skipped, non-retryable failures correctly *not* triggering a switch, and chain exhaustion still surfacing the real terminal error. Full `packages/core` suite: 1164 pass (only the pre-existing, unrelated `pty` flake documented elsewhere in this file). `packages/opencode` config tests: 230 pass. **Live-verified** against a real running V2 session server, a custom config-defined provider, and a local scripted fake LLM: scripted 3 consecutive 429s for the primary model (matching `RequestExecutor`'s real 1-initial + 2-retry budget) and a success for the configured backup — `_calls` showed the exact `{primary: 3, backup: 1}` sequence, the final assistant message correctly reported `model: backup` with the backup's scripted text, and a `model-switched` projection row was present.
- **Where:** [`dev` branch history](https://github.com/chipp-ai/opencode/commits/dev).

### Dynamic workflows

Claude-Code-style project-local workflows: a script controls orchestration deterministically (loops, branching, parallel fan-out, staged pipelines) instead of leaving it to the model, with `agent()`/`parallel()`/`pipeline()`/`phase()`/`log()`/`budget` primitives dispatching isolated subagent sessions.

- **Upstream gap:** [anomalyco/opencode#29059](https://github.com/anomalyco/opencode/issues/29059) (closed by stale-bot) and [#30308](https://github.com/anomalyco/opencode/issues/30308) (open). A substantial community implementation existed — [PR #29789](https://github.com/anomalyco/opencode/pull/29789) (still open, unmerged, `CONFLICTING`) plus a 6-PR reviewable split ([#32390](https://github.com/anomalyco/opencode/pull/32390)–[#32396](https://github.com/anomalyco/opencode/pull/32396)) — all closed unmerged by the same automated PR-cleanup bot, with zero maintainer engagement across the entire multi-month thread.
- **Origin:** design informed by the abandoned upstream attempt (~55-65% of its ~35k-line diff was reusable: discovery/meta/lint, the persisted schema, TUI dialogs, HTTP route schema); the agent-dispatch core is written from scratch against the current V2 session runner rather than reused, since the original dispatches through the legacy V1 session/prompt loop, which this repo's own architecture rules (`AGENTS.md`) say new orchestration code must not do. Also fixes a real bug found in a separate community branch's "bare globals" script format (Claude-Code-compatible bare `agent()`/`parallel()`/etc. globals): `pipeline` was defined but never actually injected, so scripts calling it threw `ReferenceError`.
- **Status — phased rollout, each phase independently shipped and tested:**
  - ✅ **Phase 0 — missing V2 primitives.** `SessionV2.wait` was a hardcoded stub; implemented for real via a new `SessionRunCoordinator.join` (awaits a key's current drain without ever force-starting one, with a `lastDone`-map fix for the case where a zero-async-boundary drain settles before the caller gets a scheduling turn). Added `parentID` to `SessionV2.create` (schema/projector/rollup already supported it end-to-end). Added `SessionHistory.lastAssistant`.
  - ✅ **Phase 1 — minimal V2-native engine.** `WorkflowAgentDispatch` (one-shot isolated subagent dispatch: ephemeral per-call `AgentV2.Info` registration with auto-cleanup, `SessionV2.create`→`prompt`→`wait`→`SessionHistory.lastAssistant`, never touching the V1 loop) and `WorkflowEngine` (the `agent`/`parallel`/`pipeline`/`phase`/`log`/`budget` orchestration core — Promise-based to match real workflow scripts, bridged to Effect via `Effect.context()`/`Effect.runPromiseWith`; USD-based budget using the cost-rollup work's own pricing, not a token pool). A provisional `opencode debug workflow <file>` CLI command makes it runnable today. Verified live against a real V2 session/runner/coordinator pipeline (unit+integration tests) and against a real provider network call.
  - ✅ **Phase 2 — structured output.** `agent(prompt, {schema})` resolves to the captured tool-call object. Deliberately avoids forcing `toolChoice: "required"` in the shared V2 runner (that logic runs for every session, not just workflows) — instead a strong system-prompt nudge plus a scoped, auto-cleaned-up `StructuredOutput` tool whose call races (`Effect.raceAll`) against session settlement and an optional timeout, interrupting the session immediately on a structured-tool win. **Known gap:** the captured value isn't deep-validated against the schema (no JSON-Schema-to-validator compiler available) — advertised via the tool description text, but a schema-violating call still succeeds rather than retrying.
  - ✅ **Phase 3a — run persistence + journal-based resume.** Every run persists to a standalone `workflow_run` table (no FK, reusable near-verbatim from the community schema) with a journal of each live `agent()` call's (prompt, opts) key and result, updated after every call so a crash loses at most one in-flight call. `resumeFromRunId` replays the journal: the unchanged prefix returns cached results at zero cost (seeding `budget.spent()` correctly), diverging to live dispatch from the first changed call onward — "same script + same args → 100% cache hit." **Known gaps:** journal position isn't guaranteed to align with source order for calls inside a single `parallel()`/`pipeline()` batch (worst case: extra live re-dispatches); no cascading cancellation of an already-in-flight dispatch when the run is interrupted (the row is correctly marked `cancelled`, but a dispatch already bridged through `Effect.runPromiseWith` keeps running).
  - ✅ **Phase 3b — worktree isolation.** `agent(prompt, {isolation: 'worktree'})` creates a fresh git worktree, dispatches into it, and always cleans up (via `Effect.acquireRelease`, so cleanup runs even when the dispatch itself fails). The engine only depends on a minimal `WorktreeProvisioner` port (`packages/core/src/workflow/engine.ts`); the real adapter wraps opencode's own `Worktree.Service` (app-layer, since it needs `InstanceStore`/`Project`/`Git`/`AppProcess`, which `packages/core` must not depend on). Calling `agent({isolation: 'worktree'})` with no provisioner configured dies loudly instead of silently ignoring isolation. Wired into the debug CLI only -- not the HTTP handler (see Phase 5's gap).
  - ✅ **Phase 4 — sandboxed script execution.** `WorkflowEngine.runSource` runs a workflow script's own source text in an isolated `node:vm` context (`packages/core/src/workflow/sandbox.ts`) with `agent`/`parallel`/`pipeline`/`phase`/`log`/`budget`/`args` as bare globals, matching the real Workflow tool's contract — including the actual `pipeline` global the community's bare-globals branch documented but never injected. No `process`/`require`/`fetch`/`Buffer`/`console`/filesystem access: a fresh `vm.createContext` starts as its own realm with none of those, and nothing here adds them back — fixing the community branch's actual security bug of running scripts via unsandboxed `new Function` in the *host* global scope. `Date.now()`/argless `new Date()`/`Math.random()` throw with an explanatory error (real Date/Math otherwise) since they'd be nondeterministic across a resumed run. **Known, honestly-scoped limitation:** `vm` is a "soft" sandbox (Node's own docs: not a defense against a genuinely malicious script) — this guards against an honest mistake in a checked-in workflow file, not untrusted third-party code.
  - ✅ **Phase 5 — HTTP API + discovery.** `.opencode/workflows/*.js` discovery: each file's metadata comes from a leading `export const meta = {name, description}` literal, extracted and evaluated in its own throwaway `vm` context — never running the rest of the file just to list it (`WorkflowDiscovery`), with a lint error reported per malformed file rather than failing discovery for the whole directory. `GET /api/workflow` (list), `POST /api/workflow/:id/run` (run to completion, returns the persisted result), `GET /api/workflow/run/:runID` (fetch a past run) routes, wired into both the client SDK and the legacy JS SDK. **Known gap:** `workflow.run` blocks for the run's full duration with no streaming progress endpoint; no `isolation: 'worktree'` support over HTTP yet (app-layer-only constraint, same as Phase 3b).
    - **A real, non-obvious multi-package type-inference trap, found and fixed along the way:** a handler that directly `yield*`s a *global* (non-Location-scoped) service — even one `routes.ts`'s own service layer already closes — breaks `effect/unstable/http`'s `HttpRouter.toWebHandler`/`HttpRouter.serve` type inference several packages away from the handler itself: `packages/cli`'s daemon-based `serve` command and `packages/sdk-next`'s embedded server both stopped typechecking, with the actual error pointing at unrelated code (an arity mismatch on `web.handler(...)`, a `Database.Service`-vs-`Daemon.Service` mismatch). `Layer.provide` closes its *caller's* requirement but never folds what it provided back into what `toWebHandler` considers resolved — every other handler in this codebase avoids the trap by only ever depending on a domain service that already closes its own Database/FSUtil dependency internally, which is exactly why `WorkflowRegistry` exists instead of the handler using `Database.Service`/`FSUtil.Service` directly. Fixed at each of the three call sites: an explicit redundant re-close (matching the pre-existing, identical workaround already there for `Credential.node`/`PermissionSaved.node`) for `packages/cli`/`packages/sdk-next`'s `Layer.build`-style boundary, and an explicit (empty, and actually correct — nothing is truly unresolved at runtime) second `Context` argument to `web.handler(...)` at the one call site where `toWebHandler`'s specific "Requires" bookkeeping didn't clear even after that.
  - ✅ **Phase 6 — TUI + slash command.** `/workflows` in the prompt opens `DialogWorkflow` (lists discovered workflows via `GET /api/workflow`, surfacing per-file lint errors inline rather than just an empty list) — selecting one runs it via `POST /api/workflow/:id/run` and reports completion/failure as a toast, mirroring the existing `/skills` dialog's structure. Also found and fixed a real bug live-testing this against the actual production server: the generated client only builds an HTTP body from fields present on the call-site object and omits it entirely when none are, but the endpoint's payload schema requires *an* object (even an empty one) -- fixed with an explicit `args: undefined` at the one call site that has nothing else to set. **Known, deliberately-scoped gap:** this is a minimal list-and-run dialog, not the community's original richer `dialog-workflow*` cluster (live progress streaming, resume-from-run picker, worktree-aware UI) — building that fully requires Phase 5's streaming-progress gap to close first, since there's nothing to stream from yet. No dedicated docs site for this fork (same call as the cost-rollup work) — this file is the documentation.
- **Where:** [`dev` branch history](https://github.com/chipp-ai/opencode/commits/dev), commits `c76c57f`..`e18c0fe` (Phase 0-3a); Phase 3b/4/5/6 land separately.
